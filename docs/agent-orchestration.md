# SaaS Factory agent orchestration V2

- Runs at minutes 00, 10, 20, 30, 40 and 50 **UTC**, contingent on the workflow being merged to `main` and Actions being enabled. GitHub schedule may be delayed or skipped.
- Always examines open issues and PRs before assignment. Never creates an issue, deploys, provisions cloud resources, or changes secrets. Only the guarded coordinator may merge a catalog-authorized PR after the complete v1 gate below.
- `agent:approved` is the explicit authorization to dispatch, with priority labels `priority:p0`, `priority:p1`, `priority:p2`. Issues must state `Files: path/to/file, directory/` on a single line. Never approve overlapping file scopes.
- A Copilot-assigned issue, in-progress/review/blocked label, or linked Copilot PR consumes capacity. Phase 1: maximum four concurrent missions (previously two); promotion to six requires verified GitHub Copilot quota, CI reliability and a separately reviewed change. Issues without scope or PRs without an issue link block unsafe dispatch.
- **GitHub partner Codex (OpenAI) shares the same four-slot limit.** A live issue assignee `Codex` or an issue-linked `codex/` PR occupies a slot even without `agent:in-progress`; an unlinked coding-agent PR fails closed. The GitHub partner is not automatically dispatched through the catalog of 45 Copilot profiles, and existing PR approvals/CI/branch protections still apply. A closed issue no longer occupies capacity; do not reuse a blocked no-diff PR as proof of implementation.
- At most one approved, unassigned issue is dispatched per pass. No newly approved issue means an idle run.
- REST Copilot assignment is in public preview and requires a user token. The dispatcher uses repository secret `COPILOT_DISPATCH_TOKEN` only in its API step, with no `GITHUB_TOKEN` fallback. Missing credentials fail before checkout; checkout uses the read-only default token without persisted credentials, and dispatch only runs on `main`. See [authorization setup and rollback](copilot-dispatch-authorization.md). A successful assignment still requires API read-back; owner setup and live validation remain required.
- Dispatcher reports: JSON artifact and job summary on each dispatch pass (currently every 10 minutes). A separate **read-only operations report** runs at 00, 06, 12, 18 UTC and on manual dispatch from `main`. The dedicated report covers verified Actions runs, CI jobs, active agent issues and PR reviews, blocking approvals and last merged PRs; missing GitHub API data is explicitly flagged `incomplete`. No inference of paid Copilot credit usage.
- Bounded recovery remains delegated to existing issue #6 / PR #16 and is disabled until a real Copilot trigger is proven. The two-attempt PR/SHA limit is a hard stop, not a simulated retry or correction loop.
- Manual verification before enabling: merge with review; check scheduled run; create a harmless approved issue with exact `Files:` scope; inspect whether GitHub accepted assignment and created a Copilot task/PR; review usage/quota from GitHub billing controls. Do not assert that assignment works from a workflow-only test.
- Do not reuse code, migrations, secrets, Mia/RAG or workflows from Project3.

## Orchestration autonome v1

`.github/scripts/factory-orchestration.cjs` exports `CONTRACT_VERSION: 1` and `run({github, context, core, io})`. It reads only `docs/catalog/factory-backlog-v1.json` from the exact `main` SHA checked out by the existing workflow. Unknown catalog fields, graph cycles, absent references, closed `not_planned` issues, mismatched role / `Files:` / `Depends-On:` fields, and incomplete API evidence fail closed. Only an exact `agent:planned` catalog issue with `automationAuthorized: true` and resolved dependencies can be promoted to `agent:approved`; the coordinator runs before candidate selection. Waiting planned issues do not consume the dispatch cap.

A PR dependency is satisfied only by `merged: true`. An issue dependency must be closed with `state_reason: completed`, retain its exact approved catalog metadata, and have a linked merged PR; alternatively, the dependency itself may declare a non-empty `acceptance` proof in the versioned catalog. Labels, closure alone, and green CI are not dependency proof.

Automatic merge is restricted to the same repository and `main`, exactly one authorized catalog issue link (including explicitly registered `existingWork`), an expected Copilot author and `copilot/` branch, non-draft status, clean mergeability and the unchanged original `main` SHA. Closing directives accept only visible local or same-repository issue references; HTML comments and fenced examples do not count, and extra or unsupported references block eligibility. The coordinator fetches detailed PR data before checking mergeability and verifies that the complete changed-file response count matches `changed_files`; destination and rename-source paths must be inside `Files:`. Workflow changes are eligible only when their exact paths are explicitly authorized in the trusted main catalog; they undergo the same final CI, scope and free-review-job checks as other files. No PR code is executed by the privileged coordinator. Required CI is identified by the canonical `.github/workflows/ci.yml` workflow identity and the newest successful run on the exact PR head SHA; older successful attempts cannot override a newer failed or pending run, and that evidence is rechecked immediately before merge. The latest unambiguously associated run for the same PR and head SHA must also contain a successful `Free deterministic PR review` job. This job checks patch integrity and forbidden tracked-secret paths; it is not an AI or human content review and does not create a GitHub approval. Effective requests for changes, unresolved threads, pending automated-review requests or incomplete API responses block the merge. A newer approval by the same reviewer supersedes an older request; a mere comment does not.

The coordinator re-reads the issue state, approval, role, priority, file scope and dependency metadata together with the PR and original `main` SHA before merging; dependencies and CI are refreshed again at the final gate. The dispatcher also revalidates the selected approved mission and its dependencies immediately before assignment. Existing #6 / PR #16 is mapped only to its declared `existingWork` pair; catalog scope updates from #16 are consumed from `main` only after that PR merges, and its explicitly authorized workflow paths receive the same automated controls. GitHub REST reads and merge are not atomic: an issue, review, dependency or base can change after the last read and before the merge request. The merge API's expected head SHA limits one race but does not protect the base or issue state; existing branch protections remain authoritative. The owner authorized the deterministic free CI gate in place of paid PR review for catalog missions. Residual API races are reported rather than described as atomic guarantees. The coordinator never enables auto-merge or changes protections.

The workflow remains `*/10`, with at most four active missions and one assignment per pass. It runs only from `main`, checks out `github.sha` with no persisted credentials, and supplies the user token only to its API step. Reports contain decisions and issue / PR identifiers, not credentials or raw API errors; sanitized partial orchestration results are persisted if a later API call fails.

Recovery is not triggered by this coordinator: the existing #6/#16 mechanism must demonstrate real Copilot triggering before activation. `retryAllowed(attempts)` implements the strict two-attempt bound for future integration; it does not claim or simulate a retry. The coordinator never retries a merge, changes code, or loops corrections.

Optional owner/team review notifications do not impose an extra human gate on catalog-authorized automation. Required reviewers and branch protections remain enforced by GitHub; an effective change request still blocks merge. No reviewer request or branch rule is deleted or changed by this policy.

Mission authorization additionally requires GitHub GraphQL `closingIssuesReferences` on the exact head SHA to contain precisely the same single local issue. Markdown parsing is only a conservative prefilter; it is not the authorization source. Missing, paginated, foreign or stale reference evidence blocks merging. Review timestamp ties are broken by review ID. After a merge advances main, assignment is deferred to the next pass, which reloads the trusted catalog/code; dispatch revalidation also binds the originally selected candidate metadata.

Merged dependency proof also requires canonical GitHub closing-issue relationships; a merged PR body alone cannot prove that it delivered or closed the required mission. This was verified read-only against merged PR #16, whose canonical closing issue is #6.

## Réveil automatique après CI verte de main (2026-11-09)

- Le workflow privilégié **séparé** `.github/workflows/saas-factory-post-main-ci-wake.yml` écoute `workflow_run` uniquement pour le workflow **SaaS Factory CI**, avec filtre de branche source `main`. Il exige un vrai `push` sur `main`, une CI terminée avec succès et un SHA identique au commit courant de `main` (données webhook et API revalidées).
- Après cette validation, son `GITHUB_TOKEN` à permission **`actions: write` limitée au seul workflow** démarre `saas-factory-agent-dispatch.yml` via `workflow_dispatch`. Il ne checkout aucun code de PR et ne manipule pas le jeton utilisateur Copilot. GitHub prend explicitement en charge `workflow_dispatch` depuis `GITHUB_TOKEN`.
- **Aucun droit d'écriture supplémentaire dans `.github/workflows/ci.yml` :** le workflow de tests de PR demeure en lecture seule, sans `COPILOT_DISPATCH_TOKEN`. La revue gratuite demeure déterministe.
- Le cron de secours est `*/10 * * * *` (UTC), conforme au catalogue. La cadence décrit la vérification de la file, pas le nombre d'exécutions d'agents facturées ; maximum quatre missions actives pour la phase 1 et une affectation par passage.
- Le coordinateur conserve tous ses contrôles : CI exacte de la PR, job de revue gratuite, périmètre, approbation issue, dépendances, revalidation SHA, protections GitHub et refus des `CHANGES_REQUESTED` ou discussions non résolues.
- **Preuve de fonctionnement exigée :** CI `push` de `main` verte → `SaaS Factory trusted post-main CI wake` vert → `SaaS Factory agent dispatch` avec événement `workflow_dispatch` → rapport d'affectation ou fusion et effets GitHub vérifiés. Une CI verte seule n'est pas une preuve de full auto.
- **Blocage GitHub Copilot :** les PR Copilot nécessitent par défaut une approbation humaine pour exécuter leurs workflows. L'administrateur du dépôt peut choisir `Settings → Copilot → Cloud agent → Actions workflow approval → Require approval for workflow runs` désactivé, en connaissance du risque d'exécuter du code généré avant revue. Ne pas contourner ce verrou via un workflow de PR avec droits d'écriture ou secrets.

## Relais automatique après la session Copilot (2026-11-09)

- Une PR produite par un agent reste parfois en brouillon après la fin de sa session. Le coordinateur peut désormais la préparer **uniquement** si la mission est explicitement autorisée, les dépendances sont livrées, le lien GitHub vers l'issue est unique, les fichiers modifiés correspondent au contrat, et la **dernière session Copilot associée est terminée avec succès**. Une session en cours, un acteur étranger ou un SHA divergent bloquent la transition.
- Si sa branche a été créée avant le dernier SHA de main, le coordinateur utilise l'API GitHub de mise à jour de branche avec `expected_head_sha` (sans force push). Un conflit ou une erreur API bloque l'opération ; le SHA suivant doit repasser tous les contrôles.
- Une fois la branche à jour, le passage de *draft* à *ready for review* exige une CI GitHub authentifiée **verte sur le SHA de tête exact**, le job `Free deterministic PR review` vert, aucun fil de discussion non résolu ni `CHANGES_REQUESTED`, et une relecture GitHub du SHA et de l'état de la PR. L'API GraphQL confirme la transition ; aucune approbation fictive n'est créée.
- Aucun brouillon n'est fusionné dans le même passage. La prochaine exécution du coordinateur recontrôle les conditions strictes de merge et laisse GitHub appliquer ses protections de branche.
- Le rapport `agent-dispatch-report-<id>` expose `orchestration.prepared` pour les transitions `branch-updated` ou `ready-for-review`. L'ancien état `idle:no-approved-missions` avec PR draft ne démontre donc pas un cycle autonome abouti.
- Ce mécanisme ne contourne **pas** la protection GitHub Actions `Require approval for workflow runs` des PR Copilot : un administrateur doit choisir de la désactiver dans les paramètres Copilot pour supprimer l'étape manuelle.

## Réveil réactif des PR Copilot (2026-11-09)

- Le workflow séparé `.github/workflows/saas-factory-copilot-ci-wake.yml` écoute les exécutions terminées de `SaaS Factory CI` sur les branches `copilot/**`. Il ne fait jamais de checkout de PR et ne possède que `actions: write`, `contents: read`, `pull-requests: read` ; la CI des PR demeure en lecture seule.
- Il vérifie de nouveau le workflow source par identifiant, chemin et nom, sa conclusion `success`, le SHA exact et la relation univoque avec une PR **ouverte, créée par Copilot, issue du même dépôt et ciblant main**. En cas de divergence, aucun dispatch n'est émis.
- Le signal `workflow_dispatch` ne vaut ni preuve de revue ni autorisation de fusion. Le coordinateur sur `main` revalide le catalogue, les dépendances, la portée des fichiers, la CI, le job gratuit de revue et toutes les protections avant toute mutation.
- Lorsqu'il a réellement converti un brouillon Copilot en PR prête à relire, le dispatcher demande **une unique réexécution** de lui-même, via son jeton utilisateur déjà autorisé. La relecture suivante décide seule de la fusion ; une simple mise à jour de branche ne provoque pas cette réexécution puisque la nouvelle CI doit d'abord réussir.
- Le cron `*/10` reste une voie de secours si GitHub retarde ou saute un événement `workflow_run`, sans augmenter la limite de deux missions actives. Les workflows de revue Copilot payante restent désactivés.
- **Critère de validation réelle :** PR Copilot synchronisée → CI PR verte → réveil Copilot PR → dispatcher `prepared:ready-for-review` → unique relance → fusion protégée → CI main verte → nouveau dispatch et mission suivante. Les API GitHub peuvent refuser les protections ou nécessiter le réglage administrateur de validation des Actions Copilot ; aucun contournement n'est prévu.

## Reprise automatique bornée des CI rouges (2026-11-09)

- Le workflow principal de CI de PR reste strictement **en lecture seule**. Le workflow séparé `saas-factory-agent-ci-recovery.yml`, chargé depuis `main`, s'exécute seulement après une CI GitHub `failure` issue d'une PR Copilot du même dépôt. Aucun code de PR n'est checkout avec des secrets.
- Le script authentifie le run CI et son workflow, le dépôt/branche/PR/SHA de tête, l'auteur Copilot, l'issue approuvée et les métadonnées du rôle avant toute action. Il relit la PR et l'issue immédiatement avant publication. Aucun commentaire de correction sur une PR fermée ou sur un ancien SHA.
- Le commentaire `@copilot` est une instruction de correction des tests, **pas une revue payante**. GitHub ne traite les mentions que depuis un utilisateur autorisé à écrire ; le workflow utilise le `COPILOT_DISPATCH_TOKEN` existant, sans l'afficher ni le transmettre à la CI de PR. L'identité du propriétaire est vérifiée avant publication.
- Le registre de tentatives vérifiable est stocké dans les commentaires GitHub avec marqueurs de SHA et run. Politique d'utilisation : **maximum 2 corrections par SHA, 4 sur la vie d'une PR**. Au-delà, arrêt explicite (`blocked`) sans nouvelle dépense IA. Le même run est idempotent.
- L'agent Copilot peut pousser une nouvelle révision ; la CI et le réveil PR relancent alors le même chemin sécurisé. L'automatisation ne force jamais une fusion ni ne passe outre un refus GitHub. Si le commentaire ne déclenche aucune session, ou si le quota est atteint, un diagnostic sera nécessaire ; le mécanisme de reprise ne doit pas être déclaré testé de bout en bout avant un échec CI réel résolu par Copilot.
